# Report 2 — Architecture Review

## Current design

```
app/
├── app.vue                  layout shell: header, mobile menu, footer, global SEO
├── app.config.ts            Nuxt UI colour tokens (primary: amber, neutral: gray)
├── assets/css/main.css      Tailwind v4 theme + component classes + motion
├── components/              AppHero, AppGalleryGrid, MediaImage, AppLogo†, TemplateMenu†
├── composables/             useLanguage, useMediaUrl, useScrollReveal†
├── data/                    business content (company, projects, services, factory, careers, ui, categories, site-images)
├── media/                   ── infrastructure ──────────────────────────
│   ├── catalog.generated.ts   AUTO-GENERATED typed catalog (paths + dimensions)
│   ├── url.ts                 buildMediaUrl / variant snapping
│   ├── presets.ts             sizes/loading/fetchpriority per use case
│   ├── fallback.ts            storage path → /public path map
│   └── project-media.ts       presentation glue (withAlt, projectCover, projectImages)
├── pages/                   7 static routes + /du-an/[slug]
├── plugins/reveal.ts        v-reveal IntersectionObserver directive
├── providers/               @nuxt/image custom provider → buildMediaUrl
└── shared/media/            constants, types, validation, manifest.json (188 KB)

scripts/media/               scan → catalog → optimize → upload → verify
scripts/check-media-literals.mjs   CI guard: no hardcoded /images/ or supabase.co in app/
```

† unreferenced (dead)

**Dependency direction is correct and deliberate.** The rule the codebase enforces is:

```
pages ──► data (business copy)  ──► shared/types
  │           │
  │           └──► media/catalog.generated (by stable mediaId only)
  │
  └──► media/* ──► shared/media/*  ──► manifest.json
```

Business content never stores a storage path or a dimension. The generated catalog never stores copy. They are joined at the presentation boundary by `withAlt(asset, altText)`. `tests/media.test.ts` actively asserts this (`catalog assets carry media only — never business copy`), and `check-media-literals.mjs` enforces it in CI. This is a real architectural boundary that is actually defended, which is rare.

The `docs/media-migration/` series documents the reasoning across five phases, including a Phase 5 that correctly anticipates `ProjectMediaId ≡ folder name` becoming an unstable primary key.

**This layer should not be redesigned. It should be protected.**

## Problem A1 — The generated catalog is not reproducible from its source of truth

**Severity: Critical** · Difficulty: Low · ~2h

`app/media/catalog.generated.ts` carries a header declaring it build output regenerated by `pnpm media:catalog` from `manifest.json`. It is not:

```console
$ pnpm media:catalog
[media:catalog] 11 projects, 11 workshop, 3 company, 1 brand
$ git diff --stat app/media/catalog.generated.ts
 app/media/catalog.generated.ts | 260 ++++++++++++++--------------
 1 file changed, 130 insertions(+), 130 deletions(-)
```

**130 of 221 asset references (59%) have stale dimensions.**

```
projects/cai-tao-nha-quan-8/3.webp
  catalog  3000×2000
  manifest 2560×1707
```

**Root cause.** `scripts/media/optimize.ts` line 14 caps masters:

```ts
const MASTER_MAX_EDGE = 2560
```

The manifest was rescanned after optimisation; the catalog was not regenerated. Because the downscale was uniform, aspect ratios survived (3000/2000 = 1.5000, 2560/1707 = 1.4997), so **no visible layout shift today**. That is luck, not design.

**Why it matters.** The system's core promise — "the catalog is derivable from the manifest" — is currently false, and *nothing detects it*. A future crop, rotation, or art-directed variant will silently ship wrong `<img width height>` and wrong `aspect-ratio` boxes in `AppGalleryGrid`.

**Recommendation.**

1. Add a CI step that fails when the committed catalog drifts:
   ```yaml
   - name: Media catalog is up to date
     run: pnpm media:catalog && git diff --exit-code app/media/catalog.generated.ts
   ```
2. Regenerate and commit the catalog now.
3. Strengthen `tests/media.test.ts` — see Problem A2.

**Benefit.** Restores the single guarantee the whole media layer rests on.

## Problem A2 — The consistency test has a hole exactly where drift occurred

**Severity: High** · Difficulty: Low · ~1h

`tests/media.test.ts:193`:

```ts
it('every catalog asset resolves to a real manifest entry', () => {
  for (const asset of everyCatalogAsset) {
    expect(manifestPaths.has(asset.path), asset.path).toBe(true)   // path only
  }
})
```

It compares **paths**, never `width`/`height`. All 26 tests pass against a 59%-stale catalog.

**Recommendation.** Assert the full asset, not just its key:

```ts
const byPath = new Map(manifest.assets.map(a => [a.path, a]))
for (const asset of everyCatalogAsset) {
  const entry = byPath.get(asset.path)
  expect(entry, asset.path).toBeDefined()
  expect({ w: asset.width, h: asset.height }, asset.path)
    .toEqual({ w: entry!.width, h: entry!.height })
}
```

**Benefit.** The test now fails on exactly the class of bug that reached `main`.

## Problem A3 — The i18n model is a cookie, not an architecture

**Severity: Critical** · Difficulty: High · ~1 week

`useLanguage()` stores the locale in a cookie and every component calls `t(...)` at render time. There is one URL per page, serving two languages.

Three separate failures fall out of this single decision:

**1. Hydration mismatch on every prerendered page.** All seven marketing routes are `prerender: true`, so the static HTML is Vietnamese with `lang="vi"`. An English visitor's cookie only takes effect on the client:

```
$ curl -H 'Cookie: lai-huy-locale=en' localhost:3000/
<html lang="vi"> … <title>Thi công & sản xuất nội thất…</title>
```
Browser console on that same load:
```
[ERROR] Hydration completed but contains mismatches.
```

**2. The English content is unindexable.** No `/en` route, no `hreflang`, no alternate URL. Search engines see one Vietnamese document per page. Every English string in `projects.ts`, `company.ts`, and `ui.ts` is invisible to Google — the translation effort currently returns zero SEO value.

**3. Cache correctness on the one SSR route.** `/du-an/[slug]` *does* honour the cookie server-side (verified: `Anh Nam Townhouse` vs `Nhà phố anh Nam`), but responds with `Set-Cookie` and **no `Vary: Cookie`**. It escapes serving the wrong language from a shared cache only because `Set-Cookie` makes most CDNs refuse to cache it at all — meaning these pages are also never edge-cached.

**Recommendation.** Move to URL-based locales. Either adopt `@nuxtjs/i18n` (`strategy: 'prefix_except_default'`, giving `/` and `/en/…`) or hand-roll the same shape. Required outcomes:

- one URL per (page, locale)
- `<html lang>` correct in the *prerendered* HTML
- `<link rel="alternate" hreflang="vi|en|x-default">` on every page
- both locales prerendered → no hydration mismatch, no `Vary` problem

**Benefit.** Unlocks the English market for search, removes the hydration error, and makes every page edge-cacheable.

## Problem A4 — The `LocalizedText` type permits untranslated content

**Severity: High** · Difficulty: Medium · ~2–3 days (mostly translation)

`app/shared/types/localization.ts`:

```ts
export type LocalizedValue<T> = T | { vi: T; en?: T }
```

A bare Vietnamese `string` satisfies `LocalizedText`. So does `{ vi, en }` with `en` omitted. The compiler therefore cannot distinguish "translated" from "not yet translated", and the codebase drifted:

| File | Bilingual objects | Vietnamese-only |
|---|---:|---|
| `ui.ts` | 50 | — |
| `projects.ts` | 127 | — |
| `company.ts` | 24 | — |
| `categories.ts` | 6 | — |
| `site-images.ts` | 4 | — |
| **`services.ts`** | **0** | all 6 services + 18 detail bullets |
| **`factory.ts`** | **0** | capabilities, machinery, workflow, QC |
| **`careers.ts`** | **0** | 6 jobs + benefits |
| **`gioi-thieu.vue`** | **0** | 14 hardcoded template strings |

Measured in-browser with the locale set to English, **29 of 45 text nodes (64%) on `/gioi-thieu` remain Vietnamese** while `<title>` is English.

**Recommendation.** Make the type demand both languages, then let `tsc` find every gap:

```ts
export type LocalizedValue<T> = { vi: T; en: T }   // both required
```

Fix the resulting type errors (they are exactly the untranslated strings). Keep `t()`'s runtime fallback as a safety net, not as the mechanism.

**Benefit.** Translation coverage becomes a compile-time guarantee instead of a hope. This is the cheapest possible enforcement and it pays for itself the first time someone adds a service.

## Problem A5 — Two scroll-reveal systems; one is dead and drags a dependency with it

**Severity: Medium** · Difficulty: Low · ~30m

| Implementation | Mechanism | Used by |
|---|---|---|
| `app/plugins/reveal.ts` | `IntersectionObserver` + `v-reveal` directive + CSS transition | every page |
| `app/composables/useScrollReveal.ts` | `motion` package + `inView()` | **nothing** |

`useScrollReveal` is referenced by zero files. Confirmed the `motion` package never reaches the browser:

```console
$ grep -rlo "motion-dom\|framer-motion\|motionValue" .output/public/_nuxt/*.js
  motion package NOT bundled -> dead dependency
```

Yet `motion@^12.38.0` sits in **`dependencies`**, not `devDependencies`.

The surviving implementation is the better one: SSR renders content visible, the client adds `.reveal-ready` to `<html>` before hiding anything, and `prefers-reduced-motion` is respected. It degrades correctly without JS. The comment at the top of `reveal.ts` explains precisely why. Keep it.

**Recommendation.** Delete `app/composables/useScrollReveal.ts` and drop `motion` from `package.json`.

## Problem A6 — `@nuxt/ui` is a heavy dependency serving one dead component

**Severity: Medium** · Difficulty: Medium · ~half day

Nuxt UI component usage across the entire `app/` tree:

```
app/components/TemplateMenu.vue:19:  <UDropdownMenu
app/components/TemplateMenu.vue:27:  <UButton
```

`TemplateMenu.vue` is an unmodified Nuxt starter leftover (it links to `starter-template.nuxt.dev`) and is **referenced by nothing**. So `@nuxt/ui` is retained for exactly two things:

1. the `<Icon>` component (actually `@nuxt/icon`, which Nuxt UI installs transitively)
2. `app.config.ts` colour tokens — which the site never uses, since it defines its own `ink-*`/`wood-*` scales in `main.css`

It also transitively pulls in `@nuxt/fonts`, which is what silently loads Inter (see Report 4).

**Recommendation.** This is a real trade-off, so decide deliberately:

- **Option A (leaner):** drop `@nuxt/ui`; add `@nuxt/icon` and `@nuxt/fonts` directly. Smaller CSS (the 215 KB `entry.css` carries 34 unused `--ui-*` custom properties), fewer transitive deps, full control over font loading. Cost: you lose an accessible component library you may want later for the contact form.
- **Option B (keep):** keep `@nuxt/ui` and *use* it — build the contact form (Report 3, Report 7) on `UForm`/`UInput`, which gives you validation and accessible field wiring for free.

Given that a real contact form is the highest-value pending feature, **Option B is the pragmatic recommendation.** Delete `TemplateMenu.vue` either way.

## Problem A7 — Business data is duplicated between a data module and a page

**Severity: Medium** · Difficulty: Low · ~1h

`app/data/factory.ts` defines `factoryCapabilities` — four metrics, Vietnamese-only.
`app/pages/index.vue:27` defines `heroMetrics` — **the same four metrics**, inline, bilingual:

```ts
// index.vue
{ label: t({ vi: 'Xưởng sản xuất và kho', en: 'Factory & warehouse' }), value: t({ vi: '3.000 m²', … }) }

// factory.ts
{ label: 'Hệ thống nhà xưởng & kho', value: '3.000 m²', description: '…' }
```

Two sources of truth for "3.000 m²", with **different labels and different translation coverage**. `/gioi-thieu` and `/nha-xuong` render `factoryCapabilities`; `/` renders `heroMetrics`. They will drift.

**Recommendation.** Make `factoryCapabilities` bilingual (falls out of A4) and have `index.vue` map over it. Delete `heroMetrics`.

## Problem A8 — Content inconsistency across data modules

**Severity: Medium** · Difficulty: Low (content decision) · ~1h

`app/data/company.ts` places the company in **Tây Ninh** (office) and **Vĩnh Long** (factory) — the post-2025 Vietnamese provincial names.

`app/data/careers.ts` advertises six jobs located in **Bến Tre** and **Long Hậu** — the pre-merger names.

A candidate reading `/tuyen-dung` and `/lien-he` sees a company that does not know where its own factory is. For a firm whose entire pitch is *"we control the process end to end"*, this is a trust leak.

**Confidence: high on the inconsistency, medium on which set is correct.** Confirm with the business, then make one module the source of truth (likely `company.addresses`) and have `careers.ts` reference it.

## Problem A9 — Route rendering strategy is inconsistent

**Severity: High** · Difficulty: Low · ~2h

`nuxt.config.ts` prerenders seven routes and omits `/du-an/[slug]`. The build confirms it:

```
.output/public/{index,du-an,dich-vu,gioi-thieu,nha-xuong,tuyen-dung,lien-he}/index.html
# no du-an/<slug>/index.html
```

The eleven project pages — the company's **portfolio, its single strongest sales asset** — are the only server-rendered routes. They are also the only ones that cannot be served from a CDN edge (they emit `Set-Cookie`). Their content is 100% static: it comes from `projects.ts` and `catalog.generated.ts` at build time.

**Recommendation.** Prerender them from the known slug list:

```ts
// nuxt.config.ts
import { projects } from './app/data/projects'

routeRules: {
  // …
  '/du-an/**': { prerender: true }
},
nitro: {
  prerender: { routes: projects.map(p => `/du-an/${p.slug}`) }
}
```

This also removes the `Vary`/`Set-Cookie` cacheability problem for those routes and makes the soft-404 fix (Report 5) trivial, because unknown slugs then hit Nuxt's real 404 handler.

## Problem A11 — Repository hygiene

**Severity: Low** · Difficulty: Trivial · ~15m

- `README.md` is the **unmodified Nuxt starter template**, complete with a "Deploy this starter to Vercel" button and links to `starter-template.nuxt.dev`. A new engineer learns nothing about `laihuy-interior` — not the media pipeline, not `pnpm media:*`, not the `USE_SUPABASE_MEDIA` flag.
- `.claude/projects/…/memory/feedback-round2.md` is **tracked in git**. Agent scratch memory does not belong in the repository.
- `.claude/worktrees/` is untracked and not in `.gitignore`.
- `.env` contains `NUXT_PUBLIC_SUPABASE_KEY`, which is absent from `.env.example` and referenced nowhere in the codebase. (It is **not** exposed to the client — `runtimeConfig.public` does not declare it — but it is undocumented drift.)

## Scalability outlook

**What scales well.** Adding a project is: drop a folder under `media-src/`, run `media:scan --write && media:catalog && media:optimize && media:upload`, add one entry to `projects.ts`. The catalog gives you a `ProjectMediaId` union type, so a typo is a compile error. This is a genuinely good authoring loop.

**What will break first.**

1. **Editing content requires a developer and a deploy.** All copy lives in `.ts` files. The marketing owner cannot change a phone number. `docs/media-migration/phase-5-roadmap.md` already anticipates the CMS; the ~1,100 lines across `data/*.ts` are the real cost of deferring it.
2. **`projects.ts` is 643 lines and growing linearly.** At ~30 projects it becomes unreviewable. Split per-project (`data/projects/khach-san-eo-gio.ts`) and barrel-export, or move to the CMS.
3. **`ProjectMediaId ≡ folder name`.** Already documented in Phase 5 D1. Renaming a folder rewrites the identifier. Correct diagnosis; act on it before the CMS, not after.
4. **`manifest.json` at 188 KB / 160 assets.** Fine as a build artefact; a problem only because it currently ships to the browser (Report 4). Once that is fixed, it scales.

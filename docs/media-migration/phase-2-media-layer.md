**Revision 2 (2026-07-04) — approved with four maintainability refinements:**
- **R4 — Plain-string paths.** `MediaPath` is `string` (type alias, not branded) with runtime validation helpers (`isValidMediaPath` / `assertMediaPath`) shared by app and scripts. Easier to serialize, validate, and evolve toward APIs/CMS payloads; existence and well-formedness are enforced by the zero-404 gate and the CI guard instead of the type system.
- **R5 — Explicit decorative images.** `alt: LocalizedText | ''` — the empty string is a deliberate, type-visible choice meaning "decorative", not an omission. Authors must still write *something*; they can no longer forget.
- **R6 — Media service module.** The layer is a directory, not a file: `app/media/` (`url.ts`, `fallback.ts`, `presets.ts`, `index.ts`) + `shared/media/` (`types.ts`, `constants.ts`, `validation.ts`, `manifest.json`). Future upload/placeholder/blurhash logic gets a natural home; `app/utils/media.ts` from rev 1 is superseded.
- **R7 — Image presets (optional suggestion, adopted).** Named presentation bundles (`hero`, `gallery`, `card`, `thumbnail`, `full`) defined once in `app/media/presets.ts` — each fixes `sizes`, loading behavior, and fetchpriority so pages declare intent (`preset="gallery"`) rather than repeating presentation rules.

File-map and type-sketch sections below should be read through these refinements; the architecture is otherwise as approved.

**Revision 3 (2026-07-05) — filesystem is canonical; business metadata stays separate:**
- `MEDIA_TOP_LEVEL_FOLDERS` changed to the business domains `['projects','company','brand']` (see Phase 1 rev 3). The URL layer, provider, validation, and `MediaImage.vue` are otherwise unchanged (all depth-agnostic already).
- **Separation of concerns (new business rule):** the filesystem regenerates *image references only* — paths, gallery hierarchy, dimensions, manifest entries. The descriptive `Project[]` business metadata in `app/data/projects.ts` (names, categories, descriptions, SEO, marketing copy) is **hand-maintained and never regenerated from the filesystem.**

> ### Media catalog — the long-term separation (implemented 2026-07-05)
>
> Business content and media now live in fully separate modules and evolve independently:
>
> - **`app/media/catalog.generated.ts`** (generated by `pnpm media:catalog` from the manifest) is the filesystem-authoritative media layer. It owns galleries, image hierarchy, dimensions and storage paths, keyed by stable identifiers (`ProjectMediaId` = project folder name, plus `workshopMedia`, `companyMedia`, `brandMedia`). It carries **no business copy** — `MediaAsset = { path, width, height }` only. A test asserts catalog assets never contain `alt`.
> - **`app/data/projects.ts`** is pure business metadata (`Project` has `mediaId?: ProjectMediaId` and **no image fields**). It references media only through the id, e.g. `id 'khach-san-eo-gio'` → `projectMedia['khach-san-eo-gio']`. This is the CMS integration point: a future CMS supplies the business record + `mediaId`; the catalog supplies media.
> - **`app/media/project-media.ts`** is the presentation boundary. `withAlt(asset, alt)` pairs a catalog `MediaAsset` with business alt copy into a renderable `MediaImage`; `projectCover`/`projectImages` resolve a `mediaId` into gallery assets. Neither side stores the other's data.
> - **Business rule outcomes:** `company/workshop` powers the Nhà xưởng gallery (`workshopMedia`). Where an existing business project has no matching filesystem folder, the folder is simply reported **absent** — no speculation about removal/rename (rule #2). Of the 6 existing `projects.ts` entries, 3 mapped to folders (`khach-san-eo-gio`, `codi-boutique-hotel`, `codi-villa-phan-thiet`); the other 3 (Anh Duy, Chily, Văn phòng Lai Huy) have no exactly-named folder and carry no `mediaId` — they render without imagery until business owners assign one. The 8 remaining filesystem projects have media in the catalog awaiting business entries.

It is treated as build output, not source. Any future generated media artifact (`*.generated.ts`) must follow the same convention: emit the banner from its generator and add it to the lint ignore list.

## Objective

Design the single application-side abstraction through which **every** image reference flows (Decision #5): the URL resolution layer, its types, the `@nuxt/image` integration, runtime configuration, and the feature-flag fallback (Decision #9) — such that no page, component, or composable knows how Supabase URLs are constructed, and switching providers (R2, Cloudflare, ImageKit…) or rolling back to `/public` is confined to this layer.

**Explicit non-goals of this phase:** uploading anything (Phase 3), the Sharp pipeline (Phase 4), the zero-404 gate script (Phase 3/4 — this phase only defines its integration point), any database work (Phase 5).

## 2.1 Architecture overview

### The one rule

> Application code holds **storage paths** (`projects/hotel/eo-gio/reception.webp`) inside typed `MediaImage` objects, and turns them into URLs **only** via this layer. A literal `/images/…` or `supabase.co` string anywhere in `app/` outside this layer is a defect — and is mechanically checked (§2.8).

### Resolution flow

```
        MediaImage { path, alt, width, height }
                        │
        ┌───────────────┴────────────────┐
        │  Media Layer (the only URL-aware code)          │
        │                                                  │
        │  flag ON  (USE_SUPABASE_MEDIA=true)              │
        │    raster + width hint → …/media/{base}-w{N}.{ext}   (variant snap)
        │    raster, no hint / master → …/media/{path}         │
        │    vector (.svg)        → …/media/{path}   (never -w)│
        │                                                  │
        │  flag OFF (fallback, Decision #8/#9)             │
        │    manifest reverse-map: path → oldPublicPath    │
        │    → "/images/projects/hotel/eo_gio/reception.png"  │
        │    no oldPublicPath (post-migration asset)?      │
        │    → Supabase URL anyway + dev-mode warning      │
        └───────────────┬────────────────┘
                        ▼
          <img src> / srcset baked into prerendered HTML
```

Because every route is prerendered, resolution happens at build time; the browser only ever sees final URLs.

## 2.2 Type design

```ts
// shared/types/media.ts — design sketch (signatures are the contract; bodies come at implementation)

type MediaPath = string & { readonly __brand: 'MediaPath' }   // constructed only via mediaPath()
                                                              // helper that validates the Phase 1
                                                              // §1.3 grammar at the call site

interface MediaImage {
  path: MediaPath
  alt: LocalizedText          // REQUIRED — existing { vi, en } shape used by useLanguage
  width: number               // master intrinsic dimensions, from manifest
  height: number
}

const MEDIA_VARIANT_WIDTHS = [400, 800, 1600] as const        // must match Phase 4 pipeline output
```

- **`alt` required and localized.** Turning the Phase 0 accessibility gap into a compile error. `AppHero` passes it through instead of hardcoding `""`.
- **`width`/`height` required.** Sourced from the manifest during the Phase 3 rewrite; rendered as attributes for CLS.
- **Branding via a constructor helper, not a cast**, so grammar violations fail at authoring time. Note honestly: TypeScript proves the path is *well-formed*, not that the object *exists* — existence is the zero-404 gate's job (Decision #10). The two checks are complementary.

## 2.3 URL construction (flag ON)

```
master:   {supabaseUrl}/storage/v1/object/public/media/{path}
variant:  same, with filename rewritten  {base}-w{N}.webp
```

- **Variant snapping:** a width request snaps **up** to the nearest `MEDIA_VARIANT_WIDTHS` entry (a 500 px slot gets `-w800`, never a stretched `-w400`); requests above the largest variant get the master. Deterministic filename arithmetic — no manifest lookup needed on the hot path.
- **Vectors (R2):** `.svg` paths always resolve to the master; width/`srcset` logic is bypassed entirely.
- **Path handling is depth-agnostic (R1):** the util splits `dirname / basename` and rewrites only the basename for variants — nesting depth is never inspected.
- **No query strings, ever** (Phase 1 §1.4 — versioning lives in filenames).

## 2.4 Fallback mechanics (flag OFF — Decisions #8 & #9)

- A reverse map `MediaPath → oldPublicPath` is **derived from the manifest** (single source of truth, R3) — either imported directly (41 entries ≈ a few KB, acceptable) or emitted as a slim generated module if the manifest's metadata weight ever matters. Decision: **direct import now**, optimize later if measured.
- Flag OFF ⇒ every migrated asset resolves to its original `/public` URL — byte-identical to today's site, because `/public/images` is untouched until Phase 4 exit (Decision #8).
- Assets added *after* migration have `oldPublicPath: null` and resolve to Supabase even when the flag is off (there is nothing local to fall back to). Dev mode logs a warning listing such assets so a rollback's blast radius is always known.
- **Honest rollback semantics on a prerendered site:** flipping `NUXT_PUBLIC_USE_SUPABASE_MEDIA` changes *build output*, so rollback = flip env var in Vercel + redeploy (~1–2 min), or faster: **Vercel "Instant Rollback"** to the previous deployment (whose HTML still contains `/public` URLs). Both paths are near-instant in practice; neither is a live toggle. The flag's real value: rollback is a **config change, not a code revert** — no PR, no merge, no conflict risk.

## 2.5 `@nuxt/image` integration

- Install `@nuxt/image`; register `supabase-media` as a **custom provider** and set it as default. No IPX/built-in provider use — on Vercel with prerendered routes, IPX would need a server or build-time processing that re-bundles images into the deployment, exactly what we're eliminating.
- The provider's `getImage(src, { modifiers })` calls the same pure util (`app/utils/media.ts`). `<NuxtImg :src="image.path" :width sizes="…">` then yields correct `srcset` over the `-w` variants with zero component-level URL knowledge.
- `MediaImage.vue` is the standard consumer; direct `<NuxtImg>` use is allowed where the skeleton treatment is unwanted (e.g. tiny inline thumbnails) — both routes go through the provider, so the one-rule holds either way.
- Hero/LCP treatment (fixes the live 6.6 MB-hero problem): `AppHero` renders eager, `fetchpriority="high"`, plus a `useHead` preload of the exact variant URL on pages where the hero is LCP.

## 2.6 Runtime config & environment

| `nuxt.config.ts` key | Env var | Default | Notes |
|---|---|---|---|
| `runtimeConfig.public.supabaseUrl` | `NUXT_PUBLIC_SUPABASE_URL` | `''` | Empty + flag ON = **build-time hard failure** with a clear message (fail loud, not 404s) |
| `runtimeConfig.public.useSupabaseMedia` | `NUXT_PUBLIC_USE_SUPABASE_MEDIA` | **`false`** | Safe default: a fresh clone with no `.env` builds today's `/public`-serving site |

- No Supabase SDK, no keys: public-bucket reads are keyless (A2) — **`supabase-js` is not added to the app** in this phase. The "integration" is string construction. Zero bundle weight, zero client secrets, nothing to leak.
- The service-role key remains script-only (Phase 1 §1.5); nothing in this phase touches it.

## 2.7 Reasoning — why this shape

- **One pure function under everything.** Composable, provider, and (later) the zero-404 gate all delegate to `app/utils/media.ts`. Divergence between `<NuxtImg>` output and `useMediaUrl` output is structurally impossible, and provider migration (Decision #5's exit criterion) is a rewrite of one pure file plus provider registration.
- **Manifest-derived fallback** avoids maintaining two path lists that could drift; the fallback map is *provably* consistent with what was uploaded (R3 makes the manifest authoritative for exactly this reason).
- **`MediaImage` as an object, not a bare path**, is what makes alt and dimensions non-optional — the two audit gaps — and is the exact shape a future CMS/`media` table returns, so Phase 5 swaps the data *source* without touching consumers.
- **Deleting `BaseImage.vue`** rather than extending it: it's unused, and reviving it under the name `MediaImage` with the `MediaImage` prop type gives a clean contract instead of a `string`-prop legacy surface (per the repo rule: remove dead code when discovered).

## 2.9 Risks

| Risk | Mitigation |
|---|---|
| A reference bypasses the layer (new page hardcodes a URL) | CI grep guard (§2.8) + `MediaPath` branding make the compliant path the path of least resistance |
| Variant-width constants drift from Phase 4 pipeline output | Single constant in `shared/` consumed by both app and pipeline; zero-404 gate checks variant URLs too, so drift = failed build, not broken images |
| Manifest import bloats the client bundle as the library grows | Measured at review (41 assets ≈ KBs); escape hatch designed: swap to a generated slim map, no consumer changes |
| Flag OFF silently shows stale `/public` images after new `-v{N}` uploads | Accepted + documented: fallback serves *pre-migration* state by definition; dev warning enumerates post-migration assets |
| `@nuxt/image` provider API changes (Nuxt 4 line) | Provider is ~20 lines delegating to our pure util; surface area is minimal and pinned |
| Alt-text authoring for 41 images is skipped under time pressure | `alt` is a required type field — the rewrite doesn't compile without it; Vietnamese/English drafts get review alongside the rename map |

## 2.11 Implementation notes (what shipped, and where it deviates from the design above)

Implemented 2026-07-04. All validation criteria in §2.10 pass. Deviations and discoveries, in decreasing order of importance:

1. **`sizes` convention (binding):** every `<NuxtImg>` `sizes` segment must be breakpoint-prefixed (`sm:100vw md:50vw…`). A bare default segment triggers a `@nuxt/image` v2 quirk that emits broken `1w`/`2w` srcset entries — discovered when the flag-ON hero resolved to the 400 px variant at every viewport. Verified fixed across all pages; documented in `app/media/presets.ts`.
2. **Provider config via `options`, not runtime config:** the custom provider receives `supabaseUrl`/`useSupabaseMedia` through `image.providers.supabaseMedia.options` in `nuxt.config.ts` (values read from env at build time) instead of `useRuntimeConfig()`/`#imports`. Equivalent for this SSG/prerender setup, avoids Nuxt 4 split-tsconfig resolution issues, and keeps the provider a pure delegate. `useMediaUrl` still reads runtime config.
3. **Path normalization:** `@nuxt/image` hands the provider `src` with a leading slash; `buildMediaUrl` strips it, otherwise the fallback map misses (this produced Supabase URLs inside a flag-OFF build during verification — now regression-tested).
4. **Module location:** the shared half lives at `app/shared/media/` (this repo keeps `shared/` under `app/`, unlike Nuxt 4's root-`shared/` convention) — `types.ts`, `constants.ts`, `validation.ts`, `manifest.json`; the app half at `app/media/` (`url.ts`, `fallback.ts`, `presets.ts`).
5. **Manifest seeded early:** all 41 assets exist in the manifest now with `status: "planned"` (a status the Phase 1 schema gains), because the flag-OFF fallback map derives from `oldPublicPath` and must work *before* anything is uploaded. Phase 3's upload script flips entries to `active` and fills checksums/bytes/variants/uploadedAt.
6. **`app.vue` did change after all** (plan said untouched): its 3 logo references moved from `/images/…` to `/logo.png` + `/logo-white.png` at the `public/` root, so the media guard can enforce a clean rule — *nothing* in `app/` may reference `/images/` — and Phase 4 can delete that whole tree. The logos still bypass the media layer by design (Category A).
7. **`og:image` routes through the layer:** `SeoEntry.ogImage` is now a `MediaPath` resolved via `useMediaUrl` in each page — with the flag ON these become absolute Supabase URLs (an SEO improvement over the previous relative paths).
8. **Tooling added:** `vitest` (18 unit tests over URL building, snapping, validation, manifest integrity), `@types/node` (required by the node tsconfig context once `nuxt.config.ts` reads env), `scripts/check-media-literals.mjs` (the CI guard), and CI steps for guard + tests.

*Phase 2 implementation is complete behind `USE_SUPABASE_MEDIA=false`. Phase 3 (upload + flag flip) is next, using the Phase 1 rename map and the seeded manifest.*
